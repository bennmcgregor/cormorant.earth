# System Guide

A living reference for the cormorant.earth wiki. Demonstrates every Quartz extension this fork adds, the frontmatter fields available, and the conventions to follow when writing new notes. This page itself is a self-example — every syntax it documents, it uses.

## How the system works

Three repos collaborate:

1. **The Obsidian vault** at `~/Documents/Zettelkasten/cormorant.earth/` — where I write. Plain markdown with Obsidian frontmatter. Never edited directly in the published site.
2. **The Quartz repo** at `~/Documents/Clothing Design/cormorant.earth/quartz/` — a fork of [jackyzha0/quartz](https://github.com/jackyzha0/quartz) v4 with custom plugins, components, and tooling. This is what builds the static site.
3. **Cloudflare Pages** — serves the static build at <https://cormorant.earth>.

Build pipeline:

```
Vault (.md files)
    │
    │  publish.py — copies notes with `publish: true` plus their attachments
    ▼
content/ (in Quartz repo)
    │
    │  npx quartz build
    │     ├─ rawFrontmatter transformer    : preserves YAML before normalization
    │     ├─ webpImageRewrite transformer  : <img>.jpg → <img>.webp + dims + eager-load
    │     ├─ mapPreview transformer        : [!map] callouts → preview mounts
    │     ├─ imageOptimizer emitter        : sharp-encodes .webp variants (content + map)
    │     └─ mapData emitter                : builds public/mapdata.json
    ▼
public/ (deploy this)
```

## Authoring standards (do these to avoid surprise)

The standards below are enforced by convention, not validation. I'm flagging them here so I'm consistent across pages.

> [!warning] Image paths in frontmatter
> **Use vault-root-relative paths.** Leading slash is tolerated. Example: `map_image: materials/aikuma-senryo/kakishibu-label.jpg`.
>
> The build *fails* on `./` prefixes (page-relative — different semantics) or paths that don't resolve to a file in `content/`. The `mapData` emitter validates this on every build; errors look like `[mapData] ben/piece: 'map_image' (foo/bar.jpg) does not exist in content/`.

> [!warning] Image embeds in body content
> **Use Obsidian wikilinks: `![[filename.ext]]`** (or `![[filename.ext|alt text]]` to set alt text). Don't use markdown image syntax `![alt](url)` for actual images, and don't write raw HTML `<img>` tags except for video posters or special cases.
>
> Wikilinks are what Obsidian renders natively, and Quartz's OFM transformer resolves them to root-relative URLs before the WebP pipeline runs. Mixing in HTML `<img>` tags makes the rehype plugin's path resolution work harder and can silently fail to set width/height attributes on subpages.

> [!warning] Wikilink targets
> **Use the shortest unambiguous form.** `[[cotton-canvas]]` if there's only one cotton-canvas page; `[[materials/maiwa/cotton-canvas]]` only if disambiguation is required. Never include the site domain like `[[cormorant.earth/materials/...]]`.

> [!warning] Frontmatter types are enforced
> Every frontmatter field has a strict type. The build *fails* if a value's type doesn't match.
>
> - `publish`, `map`, `draft` → boolean (`true` / `false`, no quotes)
> - `map_x`, `map_y`, `map_z` → integer (`147`, no quotes)
> - `map_image`, `title`, `description` → string (Obsidian-managed, quote style preserved)
>
> Set the property type in Obsidian: **Settings → Properties** → click each property → set type. Obsidian then writes idiomatic YAML automatically. To bulk-fix existing notes, run `tools/scripts/coerce-frontmatter.py --write`.

## Frontmatter fields

Every field this fork understands. Required vs. optional vs. fork-original is noted.

| Field | Required? | Type | Origin | Purpose |
|---|---|---|---|---|
| `title` | yes | string | Quartz | Page title; falls back to filename |
| `publish` | yes | bool | publish.py | Gate for inclusion in the published site |
| `description` | no | string | Quartz | Meta description (og:description); auto-generated by the Description plugin if absent |
| `map` | no | bool | fork | Whether this page appears as a tile on `/map` |
| `map_image` | yes if `map` | string | fork | Path to the tile image (vault-root-relative; leading slash tolerated) |
| `map_x` | yes if `map` | int | fork | Tile X position on canvas |
| `map_y` | yes if `map` | int | fork | Tile Y position on canvas |
| `map_z` | no | int | fork | Z-order (higher = on top); default 0 |
| `tags` | no | string[] | Quartz | Tag list |
| `draft` | no | bool | Quartz | Excludes from build if true |

### Example: full map-tile page

```yaml
---
title: Outfit for Ben
publish: true
map: true
map_image: ben/ben-full-outfit.jpg
map_x: -91
map_y: 17
map_z: 1
---
```

For LCP optimization, mark the hero image's wikilink alt-text with the `eager` token instead of using a frontmatter field — see [Image alt tokens](#image-alt-tokens) below.

### Example: regular content page

```yaml
---
title: Mulberry Silk
publish: true
description: Notes on Maiwa's handwoven mulberry silk; weight, hand, dye uptake.
---
```

## Images

The image pipeline at a glance:

1. **You write** `![[filename.jpg]]` in markdown. Drop the actual JPG/PNG into the vault next to the note (Obsidian's default attachment behavior is fine).
2. **publish.py** copies the markdown plus all attachments into `content/`. It reads the `map_image` frontmatter field to know to copy referenced map tiles too.
3. **imageOptimizer** (emitter) walks `content/` for `.jpg`/`.png`, resizes via sharp, encodes as WebP at quality 85, caches the result in `.cache/image-optimizer/`, and copies to `public/`.
4. **webpImageRewrite** (transformer) runs during HTML generation. For each `<img>`, it:
   - Reads source dimensions and stamps `width`/`height` attributes (CLS fix)
   - Rewrites `.jpg`/`.png` `src` to `.webp`
   - Applies `loading="eager" fetchpriority="high"` if the path is in the page's `eager_image` frontmatter

### Two-tier sizing

Body images encode at `CONTENT_MAX_WIDTH = 1200`. Map tiles encode at `MAP_TILE_MAX_WIDTH = 600` (= display 150 px × max zoom 2 × DPR 2), output as `foo.map.webp` alongside `foo.webp`. The `mapData` emitter writes `.map.webp` URLs into `mapdata.json`; body content uses the bare `.webp`.

The constants live in `quartz/util/imageSizes.ts`. The matching SCSS variable lives in `quartz/styles/variables.scss`. Change one — change both.

### Animated content

For short looping clips (the "GIF replacement" use case), use animated WebP encoded ≤ 600 px wide. There's no automated pipeline yet — convert manually with ffmpeg before dropping into the vault. See `_local/cormorant-animated-webp.md` for the conversion script.

For longer or higher-motion clips, fall back to MP4-as-`<video muted autoplay loop playsinline>` and write the HTML directly in the markdown body.

### `width="auto"` is fine in markdown

You can write HTML images by hand if needed:
```html
<img src="diagram.png" alt="schematic" width="auto" height="auto">
```

The transformer overwrites `width="auto"` and `height="auto"` with the actual encoded dimensions, so there's no harm in leaving them as authored. Width/height attributes drive aspect-ratio reservation only — actual rendered size is controlled by the `article img { max-width: 100%; height: auto; }` CSS rule in `quartz/styles/custom.scss`.

### Image alt tokens

The wikilink alias (the bit after the pipe in `![[file.jpg|...]]`) becomes the image's HTML `alt` attribute. The fork treats `alt` as a whitespace-delimited list of tokens, two of which trigger behavior:

| Token | Effect | Used on |
|---|---|---|
| `featured` | CSS in `quartz/styles/custom.scss` matches `[alt~="featured"]` to apply the index-page hover/styling for tile images | Index page only |
| `eager` | The `webpImageRewrite` transformer matches the `eager` token and sets `loading="eager"` and `fetchpriority="high"` on the `<img>` — use for the LCP image | Any page |

Tokens compose. The hero image on the index typically wants both:
```markdown
![[jacket-back-detail.jpg|featured eager]]
```

A hero on a content page wants only `eager`:
```markdown
![[full-outfit-front.jpg|eager]]
```

A regular alt-text wikilink doesn't include either token — its alias is just descriptive text:
```markdown
![[diagram.png|cyanotype dye curve over time]]
```

The token check is whitespace-bounded — `alt="featured-eager"` (hyphen, single token) does NOT trigger anything. Always separate tokens with spaces.

### Index featured-image link pattern (JS-free hover labels)

The full markdown pattern for an index tile that links to a page with a hover label:

```markdown
[ ![[jacket-back-detail.jpg|featured eager]]](ben/piece.md "Outfit for Ben")
```

Three things are happening in that one line:

1. **Inner Obsidian wikilink-image:** `![[jacket-back-detail.jpg|featured eager]]` — embeds the image; the alias becomes the `alt` (with both tokens).
2. **Wrapping markdown link:** `[ … ](ben/piece.md "Outfit for Ben")` — the standard markdown-link syntax, where the third argument inside the parentheses is the link's **title**. Obsidian's parser passes it through to the rendered `<a>` element's `title` attribute.
3. **Result HTML:** roughly
   ```html
   <a href="/ben/piece" title="Outfit for Ben">
     <img src="/ben/jacket-back-detail.webp"
          alt="featured eager"
          loading="eager"
          fetchpriority="high">
   </a>
   ```

The CSS in `custom.scss` then leans on those attributes to drive the entire hover/label experience without any JavaScript:

- **Desktop hover** — `::after` shows a static "Learn more →" overlay; the image gets a soft drop shadow.
- **Mobile (always-on label)** — `::after { content: attr(title) "  \2192"; }` pulls the `title` attribute off the `<a>` and displays it as a permanent label over the image, paired with a `::before` gradient for legibility.

This is why the markdown's third-argument title matters — it is the page title that surfaces on mobile. Keep it descriptive and short.

> [!warning] When adding a new tile to the index
> Use the full pattern: `[ ![[image|featured eager]]](page-slug.md "Page Title")`. Skipping the title argument leaves the mobile overlay empty. Skipping `featured` from the alt drops the entire hover/styling treatment. Skipping `eager` makes the image lazy-loaded — fine if it's not above the fold, bad if it's the LCP candidate.

## Callouts

This fork supports Obsidian's standard callout syntax plus one custom type.

### Standard Obsidian callouts (vanilla Quartz feature)

```markdown
> [!note]
> Standard note. Renders with a blue accent.

> [!warning]
> Warning callout. Yellow accent.

> [!info]
> Info callout. Cyan accent.

> [!tip]
> Tip callout. Green accent.
```

### `[!map]` (fork-original)

```markdown
> [!map]
```

Empty body. The `mapPreview` transformer replaces this with a `<div class="map-preview-root"></div>` mount point; the `MapPreview` component hydrates it client-side with a fit-view React Flow viewport showing every map node. Use it to embed a mini-map inside any note.

(The example at the top of this guide demonstrates it.)

## Map editing workflow

Two paths for repositioning tiles:

### Path 1 — Edit frontmatter directly

Set `map_x`,  `map_y`, `map_z` in the page's frontmatter. Run `publish.py` to sync. Rebuild Quartz.

### Path 2 — Use the visual editor

```sh
cd ~/Documents/Clothing\ Design/cormorant.earth/quartz/tools/map-editor
npm run dev
```

This starts:
- **Vite** on port 5173 — the React canvas, identical layout to the live `/map` page
- **Express** on port 3002 — the API that reads/writes vault frontmatter

Open <http://localhost:5173>. Drag any tile. The editor:
1. PATCHes the API with new `map_x`/`map_y`
2. The API writes the updated frontmatter back into the vault `.md` file
3. The API spawns `python3 publish.py --yes` to re-sync `content/`

Drag events coalesce — drag-and-release once, then drag again, and they queue cleanly without race conditions.

The editor reads from `$VAULT_PUBLISH_DIR` (default `~/Documents/Zettelkasten/cormorant.earth`) — if your vault lives elsewhere, set that env var.

This only works for x and y coordinates. To adjust z, you need to adjust frontmatter directly.

## Build & publish

### Local development

From the Quartz repo:
```sh
npx quartz build --serve
```

Hot-reloads on `content/` changes. View at <http://localhost:8080>. The map page is at <http://localhost:8080/map>.

### Publishing a write-up

1. Write the note in Obsidian. Set `publish: "true"`, fill in `title`, optionally add map fields.
2. Run `./publish.py` from the Quartz repo (or use the editor — it auto-publishes after every drag).
3. `git commit && git push` to your branch. Cloudflare Pages picks up the push and builds.

`publish.py` copies attachments referenced via `![[...]]` wikilinks, `![](...)` markdown image syntax, and the `map_image` frontmatter field. The `FRONTMATTER_IMAGE_FIELDS = ("map_image",)` constant in publish.py is what makes that last one work — extend it if you ever add new image-bearing frontmatter fields.

### Forcing a fresh image build

Wipe the cache when changing image-encoding constants (`CONTENT_MAX_WIDTH`, `MAP_TILE_MAX_WIDTH`, `WEBP_QUALITY`):
```sh
rm -rf .cache/image-optimizer/
npx quartz build
```

Cache filenames embed the encoding width (`foo.w1200.webp`) so changing widths normally invalidates the cache automatically. Manual wipe is for changes that don't affect the filename (quality, sharp pipeline tweaks).

## New page checklist

When creating a new note, in order:

- [ ] Frontmatter: `title`, `publish: true` (boolean, no quotes)
- [ ] Optional: `description` (recommended for pages likely to be shared)
- [ ] If the page is a map tile: `map: true`, `map_image`, `map_x`, `map_y`
- [ ] If the page has a hero image (LCP candidate): mark its wikilink alias with `eager` (e.g. `![[hero.jpg|eager]]`)
- [ ] Body images via `![[filename.ext]]` wikilinks, no exceptions
- [ ] Internal links via `[[note-name]]` wikilinks (shortest unambiguous form)
- [ ] Run `./publish.py`
- [ ] Build, inspect with DevTools — `<img>` tags should have explicit `width`/`height`; the LCP image should have `loading="eager"`
